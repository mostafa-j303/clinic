## misso-clinic — Project Instructions

Durable, project-specific rules. Read this before working in this project. Do not make the owner repeat these.

### Notifications
- The owner wants an automatic WhatsApp message sent to her whenever any of these happen: a new client registers, a new appointment is booked, a new order is placed, a new intake form is submitted.
- Chosen approach: **Meta WhatsApp Cloud API** (official, free tier, HTTP-based — same pattern as the existing Brevo email integration in `src/pages/api/send-email.ts`). Not the unofficial Baileys/whatsapp-web.js bridge (rejected: requires an always-on server outside Vercel and risks the number getting banned).
- The 4 event sources are: `src/pages/api/client/register.ts`, `src/pages/api/create-appointment-request.ts`, `src/pages/api/orders.ts`, `src/pages/api/client/submit-intake.ts`. Each does its own INSERT with no shared event bus — WhatsApp calls must be added individually after each successful insert/commit, wrapped in try/catch so a notification failure never blocks the user-facing request.
- See `plan.md` Phase 1 for the full integration plan.
- **Status: code is done, blocked on Meta.** `src/lib/whatsapp.ts`, `src/app/utils/whatsappTemplates.ts`, `src/pages/api/send-whatsapp.ts` are implemented and wired into all 4 event routes (fail-safe, never blocks the parent request). Sending currently fails with error 133010 "Account not registered" → calling `/register` returns "your business doesn't meet WhatsApp's policy requirements" (error_subcode 2388001). This requires completing **Business Verification** in Meta Business Suite (business.facebook.com → Business Portfolio → Security Center) — real business documents, days to clear, nothing further to build until then. Once verification clears and the number registers successfully, re-test via `POST /api/send-whatsapp` with `{"params":["Test","Test","Test"]}`.

### Database schema
- `sql_tables.sql` (project root) is the canonical, restorable schema dump (schema only, no data). **Any change to the database schema must be followed by regenerating this file:**
  ```
  pg_dump "$DATABASE_URL" --schema-only --no-owner --no-privileges --no-comments -f sql_tables.sql
  ```
  Then strip the `\restrict` / `\unrestrict` lines pg_dump 18 adds at the top/bottom (psql-18-only meta-commands that break pgAdmin's Query Tool and older psql clients).
- Restore instructions live in `README.md`.

  - Installed `framer-motion`. Used a real 3D technique (cursor-tracked spring-physics tilt via `useMotionValue`/`useSpring`/`useTransform`, grounded in a real 21st.dev reference component pulled via `npx @21st-dev/cli get`, not invented from scratch) — see `Hero.tsx`'s `TiltPhoto`.
  - **Deleted `Sparator.tsx` entirely** and its 3 usages in `page.tsx`. Section titles are no longer a separate floating component between sections — each section (`OurSevrices.tsx`, `Appointment.tsx`, `ProductSection.tsx`) now owns its own heading via the new `SectionHeading.tsx` (eyebrow + heading + scroll-reveal animation via `whileInView`), integrated into that section's own background/padding. `Appointment.tsx` and `ProductSection.tsx` had **no heading of their own at all** before this — they were entirely dependent on the external separator for their section title.

- **Real bugs hit and fixed while building this (worth knowing if touching Hero.tsx again):**
  - `overflow-hidden` on an element that also has `transform-style: preserve-3d` does not reliably clip in Chromium — the clipping must live on a plain (non-3D) child instead. This caused decorative blur circles to bleed past the viewport on mobile, causing real horizontal page scroll.
  - Floating badges positioned as children *inside* the same `preserve-3d` tilt context as the card had unpredictable cross-browser stacking (they'd render mostly hidden behind the card despite correct z-index/DOM order). Fix: badges must be flat siblings of the tilting element, not descendants of it.
  - Floating badges need responsive offsets (`left-2 sm:-left-16`) — a fixed large negative offset that looks good on desktop causes real horizontal viewport overflow on mobile.
  - Verify `whileInView` scroll-reveal animations with a **natural incremental scroll** (`page.mouse.wheel` in a loop) when testing via Playwright, not `scrollIntoViewIfNeeded()` — the latter can jump past the top of a tall section and make content that's actually fine look "invisible" in a screenshot.

- **Admin auth check was hitting a 404 in production, silently kicking every logged-in admin back to the homepage.** `AdminAuthContext.tsx` called `fetch('/api/check-admin')` but the real route is `src/pages/api/admin/check-admin.ts` (i.e. `/api/admin/check-admin`). Fixed by correcting the fetch path. Found via a real browser session (Playwright) logging in and hitting each admin page — do not assume admin auth "works" from code review alone again, verify with an actual session.

### Architecture notes (for future work)
- No ORM — raw SQL scattered across ~30 files in `src/pages/api/`. Backend is Pages Router API routes; UI is App Router (`src/app/`). Do not introduce a third routing pattern.
- Styling: Tailwind is the primary/target system. MUI (`material-react-table`) and Bootstrap are legacy and being phased out — don't add new MUI/Bootstrap usage.
- Admin pages (`/Setting`, `/Orders`, `/IntakeForms`, `/Appointments`) currently share the public site's Header/Footer, gated only by a client-side `isAdmin` boolean — this is being replaced with a real admin layout/route group (see `plan.md` Phase 4).
