## misso-clinic — Project Instructions

Durable, project-specific rules. Read this before working in this project. Do not make the owner repeat these.

### Notifications
- The owner wants an automatic WhatsApp message sent to her whenever any of these happen: a new client registers, a new appointment/package is requested, a new order is placed, a new intake form is submitted.
- Chosen approach: **Meta WhatsApp Cloud API** (official, free tier, HTTP-based — same pattern as the existing Brevo email integration in `src/pages/api/send-email.ts`). Not the unofficial Baileys/whatsapp-web.js bridge (rejected: requires an always-on server outside Vercel and risks the number getting banned).
- The event sources are: `src/pages/api/client/register.ts`, `src/pages/api/create-appointment-request.ts`, `src/pages/api/orders.ts`, `src/pages/api/client/submit-intake.ts`, `src/pages/api/client/book-from-credit.ts` (the 5th, added with the packages/appointments split — booking an actual visit time from an approved credit). Each does its own INSERT with no shared event bus — WhatsApp calls are added individually after each successful insert/commit, wrapped in try/catch so a notification failure never blocks the user-facing request.
- **Status: fully working (2026-08-17).** Blocked for a while on two sequential Meta-side steps, both now cleared:
  1. **Business Verification** (Meta Business Suite → Security Center) — was failing with error 133010/"Account not registered". Owner completed this with real business documents.
  2. **Message template approval** — WhatsApp Cloud API requires every message template pre-approved before sending. Originally built as one shared template (`new_notification`, 3 body placeholders, no button). When the owner wanted each message to carry a "view this record" deep-link button, that design didn't work: a WhatsApp dynamic URL button needs one *fixed base URL per template*, and the events deep-link to 4 different admin pages (`/Orders`, `/Appointments`, `/IntakeForms`, `/Users`) — one shared template can't support 4 different base URLs. **Switched to 4 separate per-event templates** (`order_notification`, `appointment_notification` — covers both appointments and packages, `intake_notification`, `registration_notification`), each with its own body (3 placeholders: event title / who / details) and its own URL button (1 placeholder: the record id, appended to that template's configured base URL in Meta). `src/lib/whatsapp.ts`'s `sendWhatsAppMessage()` takes a `WhatsAppNotification` object (`{templateName, bodyParams, buttonParam}`); `src/app/utils/whatsappTemplates.ts`'s 4 builder functions each pick their own fixed template name and take the relevant record id. All 5 event routes updated to pass the id through.
  - **Verified live, all 4 templates**: `POST /api/send-whatsapp` with `{"templateName": "<name>", "params": [...3 strings], "buttonParam": "<id>"}` for each of the 4 template names all returned `{"success":true}` with no errors in the server log — real messages delivered. Nothing further to build; this is done.

### Database schema
- `sql_tables.sql` (project root) is the canonical, restorable schema dump (schema only, no data). **Any change to the database schema must be followed by regenerating this file:**
  ```
  pg_dump "$DATABASE_URL" --schema-only --no-owner --no-privileges --no-comments -f sql_tables.sql
  ```
  Then strip the `\restrict` / `\unrestrict` lines pg_dump 18 adds at the top/bottom (psql-18-only meta-commands that break pgAdmin's Query Tool and older psql clients).
- Restore instructions live in `README.md`.

### Appointment booking & scheduling system (2026-08-16 — major feature)
The owner requested a real scheduling system to replace the old "pick any date, admin manually WhatsApps to confirm" flow. This was a full rebuild across schema, backend, and UI. Ran `npm run db:backup` before any schema change, per the standing rule.

**Data model added:**
- `appointments` gained `visit_count` and `validity_days` (both nullable — a package with neither is a plain single-visit booking, the default, unchanged from before).
- New `clinic_hours` table: one row per weekday (0=Sunday..6=Saturday), `is_closed` + `open_time`/`close_time`. Seeded all-closed by default — **the admin must explicitly set real hours in Settings before clients can book anything**, this is deliberate (see below).
- New `client_package_credits` table: one row per client+package "bundle" — `total_visits`, `remaining_visits`, `completed_visits`, `expires_at`. A client can have multiple bundles over time (e.g. buys the 16-visit package twice across two years).
- `appointment_requests` gained `client_id`, `slot_start`, `slot_end`, `credit_id`. The old `selected_date` column is kept (still populated) for backward compat with any pre-existing rows; new code reads `slot_start` preferentially, falling back to `selected_date`.
- `settings` gained `reward_threshold`/`reward_bonus` (nullable — the reward program is off unless the admin sets both).
- DB functions `get_appointments()` and `get_settings_data()` were `DROP FUNCTION` + recreated (Postgres won't let you `CREATE OR REPLACE` a function whose return columns changed) to include the new fields.
- **Status lifecycle changed**: appointment requests used to be `Pending → Sent → Cancelled`, with "Sent" meaning "admin clicked the WhatsApp button" (and that click mutated status). It's now `Pending → Confirmed → Completed`, or `→ Cancelled` from either of the first two. The WhatsApp button in the admin detail panel no longer changes status — it just opens a pre-filled `wa.me` chat; confirming/completing are now explicit separate actions. If you ever see a stray `Sent` status on an old row, treat it as equivalent to `Pending`.

**Core business logic — `src/lib/repositories/bookings.ts`, `clinicHours.ts`, `appointments.ts`:**
- `getAvailableSlots(date)`: generates 30-min slots within that weekday's clinic hours, minus any slot with a **Confirmed** booking. Pending requests never block a slot — see below.
- `createBookingRequest(...)`: transactional. If the package has `visit_count`, finds the client's active (non-expired) credit bundle for that package or creates one, decrements `remaining_visits` **at booking time** (not at confirm/complete), and blocks with `no_credits` if none remain. Also re-checks the slot isn't already Confirmed (`slot_unavailable`) right before inserting, inside the same transaction, to close the race window.
- `confirmBookingRequest(id)`: sets `Confirmed`, then **auto-cancels every other Pending request for that exact same slot_start** and refunds their credit (if any) — this is what "the other one can't take the same time" (owner's requirement #4) means in practice: multiple people can *request* the same slot, first one the admin confirms wins, everyone else auto-loses that slot and gets their visit credit back.
- `cancelBookingRequest(id)`: refunds the credit if one was consumed.
- `completeBookingRequest(id)`: only valid from `Confirmed`. Increments `completed_visits` on the credit bundle, then checks `completed_visits % reward_threshold === 0` — if so, adds `reward_bonus` to **both** `remaining_visits` and `total_visits` on that bundle. This is the "every 10 visits done → +1 free" rule (owner's requirement #10), applied automatically, no manual admin click.
- Credit consumption timing is deliberate and was one of the pre-build clarifying questions: decremented at **booking** (not confirm/complete), so a client with 0 remaining visits is blocked from even requesting another slot (owner chose this over "allow anyway, flag it" when asked).

**API routes:** `clinic-hours.ts` (public GET, for the booking calendar), `admin/clinic-hours.ts` (admin PUT), `appointment-slots.ts` (GET, requires client login — same rule as booking itself, no reason to expose the live schedule to anonymous visitors), `client/my-credits.ts` (GET own credit bundles), `create-appointment-request.ts` (rewritten: now requires `getServerSession`, takes `slotStart` instead of a free-text `selectedDate`, sends **both** WhatsApp and email server-side — previously only WhatsApp was server-side, email was fired from the client after the fact, which meant it silently never ran if the user closed the tab), `admin/update-appointment-request-status.ts` (rewritten to route `Confirmed`/`Cancelled`/`Completed` through the three repo functions above instead of a single unconditional `UPDATE`).

**UI:**

- `AppointmentFormModal.tsx` (admin package editor): added "Number of Visits" / "Valid For (days)" fields, both optional — leave blank for a single-visit package.

### Packages vs. appointments decoupled — a real re-architecture (2026-08-17)
Owner pushed back hard on the earlier booking-system design: "the package is just to give x visit so he can use this visits to set an appointments... the admin tables for appointments are different [from] to accept the package... and one for accept the appointment time. so the celender is different page and the user have like x vist in the header." **The core model, now:**
- **Buying a package** = requesting X visit credits, nothing else. No date, no time, ever, at purchase. Always lands as a Pending row with `slot_start = NULL`.
- **Approving a package** (admin) = the moment the client actually receives their visits. This is what creates the `client_package_credits` bundle — previously the bundle was created (just not decremented) the instant the client *requested* the package, before any admin approval, which was the actual bug behind the "why does the checkbox only work for one package" complaint (see below).
- **Booking an appointment** = spending one visit credit on a specific date/time, from the new `/book-appointment` page. Always creates a **brand-new** `appointment_requests` row (not a reused placeholder) — a client with 16 credits can do this 16 separate times, whenever they like, each one its own Pending row awaiting the admin's separate confirmation.
- **Admin confirming an appointment time** = unchanged from before (slot-clash check, auto-cancels+refunds competing Pending requests for the same slot).

**Root cause found while investigating**: `visit_count` (from a package's admin-configured "Number of Visits") gated the old "schedule my first visit now" checkbox — this part was never buggy. What actually made it *look* package-specific was that `createBookingRequest` created/reused a `client_package_credits` bundle **immediately at request time**, before any admin action, for any package with `visit_count` set. So a client "got" their credits (structurally) the moment they asked, with no real approval gate — not what the owner wanted, and also meant a client could see phantom credit balances for a request the admin hadn't even looked at yet.

**Repository changes (`bookings.ts`)**:
- `createBookingRequest`: the credit-bundle create/reuse/consume block is now gated on `visit_count && input.slotStart` together, not `visit_count` alone. A plain client package request (`visit_count` set, no `slotStart`) now touches `client_package_credits` **not at all** — `credit_id` stays null. The only way this combination (`visit_count` + `slotStart` together) still happens is the admin's own "+ New Booking" walk-in flow, which stays exactly as it was (admin is authoritative, so immediate credit + immediate Confirmed is correct there).
- `confirmBookingRequest`: now branches on `slot_start`. `NULL` → this is a package approval: creates the `client_package_credits` bundle (total/remaining = the package's `visit_count`, `expires_at` from `validity_days`) and links it back via `credit_id` on the request row, which then sits Confirmed forever as a historical "package approved" record — it never gets a slot attached to it afterward. Not-null → unchanged, the original slot-clash-check-then-confirm-then-cancel-competitors logic.
- **New** `createAppointmentFromCredit(clientId, creditId, slotStart, ...)` — the `/book-appointment` page's booking action. Locks the credit row, checks it belongs to the client / isn't expired / has `remaining_visits > 0`, checks the slot isn't already Confirmed elsewhere, decrements the credit, inserts a fresh Pending `appointment_requests` row (payment method recorded as `"Package Credit"`, price pulled from the package's own price for record-keeping — no real payment happens at this step, it happened when the package was approved).
- **Removed** (replaced by the above, no longer had a coherent purpose under the new model): `scheduleRequestSlot`, `getUnscheduledRequestsForClient`, and their 3 API routes (`admin/schedule-appointment-request.ts`, `client/schedule-visit.ts`, `client/unscheduled-visits.ts`) — these implemented the old "one deferred placeholder row gets its slot filled in once" design, which only ever supported a client's *first* visit on a package, never a second or third. `getClientCredits`/`/api/client/my-credits` was untouched — still the one shared source for a client's credit balances, now used by the dashboard, the header badge, and `/book-appointment`.

### Admin logout could lose the race against closing the browser (2026-08-17)
Owner: "when i logout form admin or client and close the site... they are still login." Tested the actual logout mechanism thoroughly first (fresh tabs, and a full simulated browser-restart via saved/reloaded storage state) — both admin and client logout correctly destroyed their session cookies in every test, so this wasn't a "logout doesn't work" bug in the way it first sounded.

The real, found issue: `handleLogout` in both `Header.tsx` and `AdminShell.tsx` did `await fetch("/api/admin/logout")` with no `keepalive` flag. If the admin clicks Logout and then closes the tab/browser fast enough, the browser can abort that in-flight request before the server ever runs `session.destroy()` — meaning the cookie survives untouched and the next visit is still logged in. Fixed both call sites to pass `{ keepalive: true }`.
- **Client (customer) logout was not changed** — it goes through NextAuth's own `signOut()`, which does a same-tab navigation after the request completes rather than an abrupt close, already a more robust pattern than the custom admin code had; not something this app's code controls the internals of.

Added `pageshow` (fires on back-forward-cache tab restores) and `visibilitychange` listeners that re-verify with the server whenever the tab becomes visible again — belt-and-suspenders against a stale "still logged in" UI painting from cached React state before a real server check runs, independent of the keepalive fix above.
- **Verified live**: logged in as admin, clicked Logout, immediately re-checked `/api/admin/check-admin` — correctly `false`. `npx tsc --noEmit` clean, full `npm run test:e2e` 15/15 (including the existing "Logout works" spec), `npm run build` clean. Could not directly simulate "browser closes mid-request" in an automated test (that's inherently a race no test harness reproduces deterministically) — the fix is the well-established browser-level mechanism (`keepalive`) for exactly this scenario, not a guess.

### Two real bugs behind "can't update some Settings fields on mobile" (2026-08-17)
Owner: "in mobile the admin still can not change the setting some fields are not working." Investigated with real touch-emulated testing (iPhone 12 device profile, `tap()` + `keyboard.type()`, not just visual screenshots) rather than guessing — found two separate, confirmed bugs:

**1. The color hex fields** (from the earlier "can't type an exact hex code" fix) had `maxLength={7}` — exactly the length of a full `#rrggbb` value. Tapping into an already-full field on mobile places the cursor without selecting the existing text (unlike a desktop double-click habit), so typing had nowhere to go and silently did nothing. Fixed by adding `onFocus={(e) => e.target.select()}` so tapping in always selects the current value, ready to be typed over — standard pattern for short precise-value fields like this.

**2. The real, bigger bug: the entire Social Links section (Facebook/Tiktok/Instagram/Mail) silently rejected all typed input, on every device, not just mobile** — mobile just made it obvious because tapping-to-retype is the natural mobile interaction, while a desktop admin might have been dragging to select text and not noticing the snap-back as clearly. Root cause: `socialEntries = useMemo(() => Object.entries(formData.social), [formData?.social])` was keyed on `formData.social`'s object *reference* — but `handleChange` mutated that nested object **in place** rather than cloning it (a leftover from before this session's edits added the phone-field special-casing to this section), so the reference never changed and the memo never recomputed. Every keystroke's `onChange` did technically fire and update the real (mutated) object, but the next render immediately snapped the controlled `<input value=...>` back to the stale memoized entry — visually and at the DOM level — before the next keystroke could register, making the field appear completely inert.
- Fixed at the root: `handleChange` now properly clones each level of a nested path (`{...prev, [parentKey]: {...prev[parentKey], [childKey]: value}}`) instead of mutating in place — this is what should have been happening all along, and prevents this whole class of "stale memo" bug from recurring anywhere else in this file. Also removed the `useMemo` around `socialEntries` entirely (6 entries is too cheap to be worth memoizing, and it was the thing that broke) — now recomputed plainly every render.
- **Verified live** with real touch-tap tests before and after: Facebook/Tiktok/Instagram/Mail all confirmed silently rejecting input beforehand, all confirmed accepting it after the fix. Did a full save→reload→verify→restore round-trip on a real field (Tiktok) to confirm the fix persists correctly end to end, not just visually. `npx tsc --noEmit` clean, full `npm run test:e2e` 15/15, `npm run build` clean.
- **Swept every other field in Settings for the same class of bug** (any `useMemo`/derived-array keyed on a nested object formData mutates) — nothing else in this file uses that pattern, so this was the only place affected.

### The real logout bug — only reproducible in production, never in local dev (2026-08-17)
Owner reported logout "still continuing" even after the keepalive fix, specifically: log out from either the admin nav sidebar or header, refresh the page, still shows logged in. Tried hard to reproduce locally first — logging out via every button, with a real `page.reload()` (not just a new tab) — and it worked correctly every single time. That consistent gap (can't reproduce locally, 100% reproducible for the owner) was the actual clue: **the owner was testing on the live production site (`stay-well-clinic.vercel.app`), and local dev has no CDN/edge caching layer at all** — this class of bug structurally cannot happen locally.

Confirmed via `curl -sI` against the real production URL: `/api/admin/check-admin` (the exact endpoint the browser polls to answer "am I logged in?") was returning `cache-control: public, max-age=0, must-revalidate` with an `etag` — Vercel/Next.js's *default* header for any Pages Router API route that doesn't explicitly opt out of caching, applied here even though this route's answer depends entirely on the request's session cookie. A `public` cache directive with no `Vary` on the session cookie means a shared cache (browser HTTP cache or Vercel's edge) is free to serve one stored answer regardless of which session actually made the request — exactly the shape of bug that would show "still logged in" after a real logout+refresh in production, while being completely invisible in local dev.

Fixed centrally: `getSession()` in `lib/session.ts` now sets `Cache-Control: no-store, must-revalidate` on every response, since every route that calls it (or `requireAdmin`, which calls it) is inherently session-dependent. This covers `check-admin.ts`, `logout.ts`, and every other admin-gated route automatically — one fix point rather than patching each route file individually, and it protects any admin route added in the future too.
- **Verified locally** that the header is now correctly set (`curl -I http://localhost:3000/api/admin/check-admin` → `Cache-Control: no-store, must-revalidate`). Could not verify the actual production caching *behavior change* without deploying, since this bug only manifests where a CDN/edge cache layer exists — local dev and a plain `npm run build` both structurally can't exercise it. `npx tsc --noEmit` clean, full `npm run test:e2e` 15/15, `npm run build` clean.
- **This fix does nothing until it's actually deployed** — unlike every other fix this session, which took effect as soon as the local dev server picked up the change, this one only matters on the real Vercel deployment (the exact environment where the bug occurs). Needs a commit + push to whatever branch triggers the production deploy, then a real re-test on the live site (log out, refresh, confirm logged out) to close the loop.
