## misso-clinic — Project Instructions

Durable, project-specific rules. Read this before working in this project. Do not make the owner repeat these.

### Notifications
- The owner wants an automatic WhatsApp message sent to her whenever any of these happen: a new client registers, a new appointment is booked, a new order is placed, a new intake form is submitted.
- Chosen approach: **Meta WhatsApp Cloud API** (official, free tier, HTTP-based — same pattern as the existing Brevo email integration in `src/pages/api/send-email.ts`). Not the unofficial Baileys/whatsapp-web.js bridge (rejected: requires an always-on server outside Vercel and risks the number getting banned).
- The 4 event sources are: `src/pages/api/client/register.ts`, `src/pages/api/create-appointment-request.ts`, `src/pages/api/orders.ts`, `src/pages/api/client/submit-intake.ts`. Each does its own INSERT with no shared event bus — WhatsApp calls must be added individually after each successful insert/commit, wrapped in try/catch so a notification failure never blocks the user-facing request.
- See `plan.md` Phase 1 for the full integration plan.
- **Status: code is done, blocked on Meta.** `src/lib/whatsapp.ts`, `src/app/utils/whatsappTemplates.ts`, `src/pages/api/send-whatsapp.ts` are implemented and wired into all 4 event routes (fail-safe, never blocks the parent request). Sending currently fails with error 133010 "Account not registered" → calling `/register` returns "your business doesn't meet WhatsApp's policy requirements" (error_subcode 2388001). This requires completing **Business Verification** in Meta Business Suite (business.facebook.com → Business Portfolio → Security Center) — real business documents, days to clear, nothing further to build until then. Once verification clears and the number registers successfully, re-test via `POST /api/send-whatsapp` with `{"params":["Test","Test","Test"]}`.

### Database schema
- `sql_tables.sql` (project root) is the canonical, restorable schema dump (schema only, no data). **Any change to the database schema must be followed by regenerating this file:**
  ```
  pg_dump "$DATABASE_URL" --schema-only --no-owner --no-privileges --no-comments -f sql_tables.sql
  ```
  Then strip the `\restrict` / `\unrestrict` lines pg_dump 18 adds at the top/bottom (psql-18-only meta-commands that break pgAdmin's Query Tool and older psql clients).
- Restore instructions live in `README.md`.

### Email (Brevo)
- Sender is a fixed Gmail address (`BREVO_SENDER_EMAIL=stay.well.clinic.3@gmail.com`), verified once in Brevo — this is already correct, do not change to per-request/dynamic sender addresses. Sender verification in Brevo is one-time, not per-email; there is no "manual approval per send" step.
- Decision (confirmed with owner): keep the free Gmail sender rather than buying a custom domain for proper SPF/DKIM domain authentication. Tradeoff accepted: emails may occasionally land in spam since Gmail's own records don't authorize Brevo's servers. - Recipients are always pulled from `settings.social.mail` (admin email in the Settings page) — this is intentional, not a bug.

Registration's email (`generateRegistrationEmailHTML` in `emailTemplates.ts`, wired in `src/pages/api/client/register.ts`) was added after the fact to close a gap where it only had WhatsApp.

### Images
- **Status: done.** Images live in Vercel Blob (public access store), not in Postgres. `images`/`product_images` tables only hold `image_url text NOT NULL` — the old `bytea` columns are gone. Uploads use `@vercel/blob`'s `put()` (see `src/pages/api/add-product.ts`, `edit-product.ts`); do not reintroduce bytea columns or base64 data URIs. Requires `BLOB_READ_WRITE_TOKEN` in env (also needed in Vercel's project env vars for production). Note: the Blob store must have **public** access — Vercel's UI does not expose a toggle to change this after creation, so if a store ever needs recreating, check for a public/private choice at creation time only.
- `next.config.mjs` whitelists `*.public.blob.vercel-storage.com` for `next/image` — required for the logo/hero images to render.
- One-off migration script `scripts/migrate-images-to-blob.ts` (`npm run migrate:images`) was used to move pre-existing DB images out; safe to re-run (skips rows that already have an `image_url`), not part of the normal dev workflow.

- **Real bugs hit and fixed while building this (worth knowing if touching Hero.tsx again):**
  - `overflow-hidden` on an element that also has `transform-style: preserve-3d` does not reliably clip in Chromium — the clipping must live on a plain (non-3D) child instead. This caused decorative blur circles to bleed past the viewport on mobile, causing real horizontal page scroll.
  - Floating badges positioned as children *inside* the same `preserve-3d` tilt context as the card had unpredictable cross-browser stacking (they'd render mostly hidden behind the card despite correct z-index/DOM order). Fix: badges must be flat siblings of the tilting element, not descendants of it.
  - Floating badges need responsive offsets (`left-2 sm:-left-16`) — a fixed large negative offset that looks good on desktop causes real horizontal viewport overflow on mobile.
  - Verify `whileInView` scroll-reveal animations with a **natural incremental scroll** (`page.mouse.wheel` in a loop) when testing via Playwright, not `scrollIntoViewIfNeeded()` — the latter can jump past the top of a tall section and make content that's actually fine look "invisible" in a screenshot.

### Appointment booking & scheduling system (2026-08-16 — major feature)
The owner requested a real scheduling system to replace the old "pick any date, admin manually WhatsApps to confirm" flow. This was a full rebuild across schema, backend, and UI. Ran `npm run db:backup` before any schema change, per the standing rule.

**Data model added:**
- `appointments` gained `visit_count` and `validity_days` (both nullable — a package with neither is a plain single-visit booking, the default, unchanged from before).
- New `clinic_hours` table: one row per weekday (0=Sunday..6=Saturday), `is_closed` + `open_time`/`close_time`. Seeded all-closed by default — **the admin must explicitly set real hours in Settings before clients can book anything**, this is deliberate (see below).
- New `client_package_credits` table: one row per client+package "bundle" — `total_visits`, `remaining_visits`, `completed_visits`, `expires_at`. A client can have multiple bundles over time (e.g. buys the 16-visit package twice across two years).
- `appointment_requests` gained `client_id`, `slot_start`, `slot_end`, `credit_id`. The old `selected_date` column is kept (still populated) for backward compat with any pre-existing rows; new code reads `slot_start` preferentially, falling back to `selected_date`.
- `settings` gained `reward_threshold`/`reward_bonus` (nullable — the reward program is off unless the admin sets both).
- DB functions `get_appointments()` and `get_settings_data()` were `DROP FUNCTION` + recreated (Postgres won't let you `CREATE OR REPLACE` a function whose return columns changed) to include the new fields.
- **Status lifecycle changed**: appointment requests used to be `Pending → Sent → Cancelled`, with "Sent" meaning "admin clicked the WhatsApp button" (and that click mutated status). It's now `Pending → Confirmed → Completed`, or `→ Cancelled` from either of the first two. The WhatsApp button in the admin detail panel no longer changes status — it just opens a pre-filled `wa.me` chat; confirming/completing are now explicit separate actions. If you ever see a stray `Sent` status on an old row, treat it as equivalent to `Pending`.

**Core business logic — `src/lib/repositories/bookings.ts`, `clinicHours.ts`, `appointments.ts`:**
- `getAvailableSlots(date)`: generates 30-min slots within that weekday's clinic hours, minus any slot with a **Confirmed** booking. Pending requests never block a slot — see below.
- `createBookingRequest(...)`: transactional. If the package has `visit_count`, finds the client's active (non-expired) credit bundle for that package or creates one, decrements `remaining_visits` **at booking time** (not at confirm/complete), and blocks with `no_credits` if none remain. Also re-checks the slot isn't already Confirmed (`slot_unavailable`) right before inserting, inside the same transaction, to close the race window.
- `confirmBookingRequest(id)`: sets `Confirmed`, then **auto-cancels every other Pending request for that exact same slot_start** and refunds their credit (if any) — this is what "the other one can't take the same time" (owner's requirement #4) means in practice: multiple people can *request* the same slot, first one the admin confirms wins, everyone else auto-loses that slot and gets their visit credit back.
- `cancelBookingRequest(id)`: refunds the credit if one was consumed.
- `completeBookingRequest(id)`: only valid from `Confirmed`. Increments `completed_visits` on the credit bundle, then checks `completed_visits % reward_threshold === 0` — if so, adds `reward_bonus` to **both** `remaining_visits` and `total_visits` on that bundle. This is the "every 10 visits done → +1 free" rule (owner's requirement #10), applied automatically, no manual admin click.
- Credit consumption timing is deliberate and was one of the pre-build clarifying questions: decremented at **booking** (not confirm/complete), so a client with 0 remaining visits is blocked from even requesting another slot (owner chose this over "allow anyway, flag it" when asked).

**API routes:** `clinic-hours.ts` (public GET, for the booking calendar), `admin/clinic-hours.ts` (admin PUT), `appointment-slots.ts` (GET, requires client login — same rule as booking itself, no reason to expose the live schedule to anonymous visitors), `client/my-credits.ts` (GET own credit bundles), `create-appointment-request.ts` (rewritten: now requires `getServerSession`, takes `slotStart` instead of a free-text `selectedDate`, sends **both** WhatsApp and email server-side — previously only WhatsApp was server-side, email was fired from the client after the fact, which meant it silently never ran if the user closed the tab), `admin/update-appointment-request-status.ts` (rewritten to route `Confirmed`/`Cancelled`/`Completed` through the three repo functions above instead of a single unconditional `UPDATE`).

**UI:**

Submit is disabled until a slot is picked and (if applicable) they have credits.
- `AppointmentFormModal.tsx` (admin package editor): added "Number of Visits" / "Valid For (days)" fields, both optional — leave blank for a single-visit package.

Each day shows colored dots for that day's non-cancelled requests (yellow=Pending, blue=Confirmed, green=Completed, red=Cancelled); clicking a day lists that day's appointments with time in a side panel. ### Architecture notes (for future work)
- No ORM. Backend is Pages Router API routes; UI is App Router (`src/app/`). Do not introduce a third routing pattern. **`src/lib/repositories/{appointments,products,orders,clients}.ts` now exist (2026-08-16)** — all DB access for those 4 entities lives there, not inline in route files; 19 route files were refactored to call them (see `plan.md` Phase 4 for the exact list). Routes still own method checks, `requireAdmin`, validation, and side effects (WhatsApp/email/blob upload) — only the SQL moved. Category, settings/image, and admin-auth routes were deliberately left inline (not part of the plan's named 4 entities). If adding a new query for one of the 4 covered entities, add it to the matching repository file rather than writing inline SQL in a route.
- Styling: Tailwind is the primary/target system. **MUI and Bootstrap are fully gone (2026-08-16)**, not just "being phased out" — `material-react-table`, `@mui/material`, `@mui/icons-material`, `@emotion/react`, `@emotion/styled` were all uninstalled after `Orders`/`Appointments`/`IntakeForms` were rebuilt on a new shared `src/app/_components/AdminTable.tsx` (sortable headers, expandable detail-panel rows, client-side pagination — see below). `react-bootstrap`/`bootstrap` had already reached zero usage before this. Don't reintroduce either.
- **Admin pages now have real server-side route protection (2026-08-16), closing the gap this note used to describe.** Each of `Setting`, `Orders`, `IntakeForms`, `Appointments` was split into a thin async Server Component `page.tsx` (checks `getIronSession(await cookies(), sessionOptions)`, `redirect("/")`s non-admins before any client bundle ships) plus the original component renamed to `<Route>Client.tsx`. They still share `AdminShell.tsx` (not the public Header/Footer) via the existing `ADMIN_ROUTES` pathname check in `layout.tsx` — that part is unchanged. A real App Router route-group (`(admin)/`) move was deliberately still not done (would touch import depth across dozens of files); the server-side session check achieves the real protection the plan wanted without that risk. If a new admin page/route is added, give it the same `page.tsx` (server gate) + `<Name>Client.tsx` (actual UI) split, add it to `ADMIN_ROUTES` in `layout.tsx`, and wrap it in `<AdminShell>` — the same 3 steps as before, plus the new server-gate step.
- **Dark mode now covers the full customer-facing app, not just the homepage (2026-08-16).** `Cart.tsx` (the header dropdown), `Cart/page.tsx` (checkout), `client-portal/page.tsx`, `client-dashboard/page.tsx`, and `intake-form/page.tsx` all got the same `dark:` class pairing used on the homepage sections. Admin pages/modals were deliberately left alone — they have no dark background styling at all, so their `text-gray-900`-style text is correct as-is on their still-white surfaces; don't add `dark:text-white` there without also giving the surface a dark background, or the text goes invisible.
- **A real, committed Playwright E2E suite now exists (2026-08-16)** — `e2e/` + `playwright.config.ts`, `npm run test:e2e`. See `plan.md` Phase 7 for what it covers, the safety rule about this project having no separate test database (specs never call data-writing endpoints — UI-state assertions only), and 4 concrete Playwright gotchas hit while writing it (cart state dies on `page.goto()`, one-shot `page.url()` reads race client-side nav, an async-fetch button click needs `page.waitForResponse()` before the next step, and `fullyParallel` fights a single dev-server instance). Read that before adding new specs.
